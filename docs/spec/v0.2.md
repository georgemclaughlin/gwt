# GWT Language Specification v0.2

Status: implemented.

GWT v0.2 is an executable behavior language built around public named
`REQUEST` flows and reusable `GIVEN / WHEN / THEN` behavior. The full EBNF is
maintained in [../grammar.md](../grammar.md).
Executable conformance coverage lives in
[`../../tests/test_spec_v02.py`](../../tests/test_spec_v02.py).

v0.2 replaces the v0.1 public boundary. Top-level `REQUEST path is Type`,
top-level `OUTPUT path is Type`, `EXPORT`, inferred entry candidates, and
`--entry` are not the public interface. A named `REQUEST <natural phrase>` is
the callable unit.

## Source Files

- Source files are UTF-8 text.
- `#` starts a comment. Comments run to the end of the line.
- Blank lines and comments do not affect execution.
- Indentation is significant and uses two spaces per level.
- Top-level forms start at column 1.
- A formatted file ends with one trailing newline.

`gwt format` is the canonical formatter. It validates syntax, normalizes
whitespace and table columns, and validates the formatted result before writing.

## Program Shape

A file may contain these top-level forms:

- optional `PROGRAM` metadata
- zero or more `USE` imports
- zero or more `RECORD` contracts, including one-of records
- zero or more named `REQUEST` blocks
- zero or more block-form `WHEN` behavior definitions
- optional `BACKGROUND`
- zero or more explicit `SCENARIO` blocks
- or one implicit `Main` scenario when no explicit scenario exists

Imports contribute records, named requests, and behavior definitions. Imported
scenarios do not run. Duplicate named requests are rejected.

## Named Requests

A named request is the public callable unit:

```gwt
PROGRAM inventory allocation

REQUEST fulfill order
  GIVEN order is OrderRequest
  AND inventory is InventoryState

  GIVEN fulfillment is FulfillmentState
    requested_units: 0
    reserved_units: 0
    backordered_units: 0
    status: "new"
    reason: "new"

  WHEN fulfill order from inventory into fulfillment

  OUTPUT fulfillment is FulfillmentState
  AND inventory is InventoryState

  THEN fulfillment.status != "new"
```

Request body forms:

- `GIVEN path is Type` without a body declares caller-provided input.
- `GIVEN path is Type` with an indented record body creates request-local setup
  state and validates it against `Type`.
- Other `GIVEN` forms create request-local setup state.
- `WHEN command` calls reusable behavior or a built-in statement. It does not
  define behavior.
- `OUTPUT path is Type` declares response shape and returned state paths.
- `THEN condition` or `THEN path is ...` declares a request postcondition.

Each named request must contain at least one `WHEN`. `OUTPUT` and `THEN` are
separate: `OUTPUT` is the response contract; `THEN` is an assertion.

## Scenarios

Each scenario runs independently with fresh state:

1. Register named requests and behavior definitions.
2. Run `BACKGROUND` setup.
3. Run scenario `GIVEN` setup.
4. Execute scenario `REQUEST` and `WHEN` steps in source order.
5. Evaluate scenario `THEN` assertions.

Single-line `REQUEST name` in a scenario invokes a named public request using
the current scenario state:

```gwt
SCENARIO partial allocation
GIVEN order is OrderRequest
  order_id: "LIST-100"
  payment_status: "paid"
  fraud_score: 12
  expedited: true
  items: []

GIVEN inventory is InventoryState
  items: []

REQUEST fulfill order

THEN fulfillment.status == "partial"
```

Single-line `WHEN command` still calls reusable behavior directly. This lets a
scenario test either the public request boundary (`REQUEST fulfill order`) or a
helper behavior (`WHEN reserve item into fulfillment`).

When a scenario contains an `EXAMPLES` table, each row creates one scenario run.

## Request Execution

When a named request is invoked:

1. Validate caller-provided `GIVEN path is Type` inputs against current state.
2. Run request-local `GIVEN` setup.
3. Run request `WHEN` calls in source order.
4. Validate declared `OUTPUT` paths.
5. Evaluate request `THEN` assertions.
6. Return only declared `OUTPUT` paths as `result`.

The full final state remains available in the execution envelope as `state`.

JSON execution uses an explicit request name:

```sh
gwt run rules.gwt --json-input request.json --request "fulfill order" --json
```

JSON state is loaded after background setup and before named-request input
validation. `.gwt` request-file mode can set up state and then call one or more
public requests. Request files cannot define behavior or named requests, and
they cannot declare `PROGRAM` or use direct single-line `WHEN` calls:

```gwt
GIVEN order is OrderRequest
  order_id: "LIST-100"
  items: []

GIVEN inventory is InventoryState
  items: []

REQUEST fulfill order
```

## Behavior

Block-form `WHEN` defines reusable behavior. Single-line `WHEN` executes
behavior or a built-in statement.

Preferred signatures mark parameters explicitly:

```gwt
WHEN deposit <amount> into <account>
  GIVEN amount is number
  add amount to account.balance
```

Behavior contracts appear before executable statements. `THEN returns Type`
declares a return value:

```gwt
WHEN cart total for <cart>
  GIVEN cart is Cart
  THEN returns number
  RETURN cart.total
```

Behavior names cannot be built-ins or behavior-body keywords: `set`, `add`,
`subtract`, `append`, `count`, `sum`, `find`, `exists`, `print`, `LET`,
`REQUIRE`, `RETURN`, `PASS`, `IF`, `ELSE`, `FOR`, `FIND`, `DECIDE`, or
`DEPENDING`.

## Types

Supported type syntax:

- `number`
- `integer`
- `decimal`
- `text`
- `boolean`
- `list`
- `any`
- a declared record name, including a one-of record name
- `list<TypeName>`, where `TypeName` is a primitive type or declared record name
- literal unions such as `"new" | "approved" | "denied"`

`integer` is an exact whole number. `decimal` is a finite exact base-10 decimal
value. `number` is the broad numeric type and accepts integers, decimals, and
host numeric values.

At JSON boundaries, `decimal` accepts finite exact decimal strings such as
`"12.30"` and integer JSON numbers such as `12`. API/CLI payloads serialize
`decimal` values as strings. GWT has no source-level `null` literal and no
nullable type modifier; JSON `null` only satisfies `any`.

Records define state shape only. They do not define methods. `RECORD` is the
only source spelling for record contracts.

## Statements

Behavior bodies support:

- `LET name be expression`
- `REQUIRE condition`
- `IF condition` / `ELSE`
- `FOR name in expression`
- `FOR name in expression WHERE condition`
- `FIND name in expression WHERE condition` with required `ELSE`
- `DECIDE` with one or more `WHEN condition` branches and required `ELSE`
- `DEPENDING ON expression` with literal or one-of kind branches
- `RETURN expression`
- `PASS`
- behavior calls
- built-ins

Built-ins:

```gwt
set path to expression
add expression to path
subtract expression from path
append expression to path
count expression into path
sum expression into path
sum name.field in expression into path
find name in expression where condition into path
find optional name in expression where condition into path
exists name in expression where condition into path
print expression
```

Conditions support symbolic boolean expressions such as `status == "ok"`,
`amount >= limit`, `not failed`, and `name contains "api"`, plus English
aliases such as `amount is at least limit`.

`DECIDE` is valid only inside behavior bodies:

```gwt
DECIDE
  WHEN amount >= limit
    set decision.status to "review"
  WHEN amount > 0
    set decision.status to "approved"
  ELSE
    set decision.status to "denied"
```

Branches are evaluated from top to bottom. Exactly the first true branch runs;
if no branch is true, `ELSE` runs. There is no fallthrough and no expression
form.

## API Payloads

Run payloads use a stable envelope:

```json
{
  "ok": true,
  "file": "rules.gwt",
  "request_file": "request.gwt",
  "scenario_count": 1,
  "scenarios": [],
  "state": {},
  "result": {},
  "output": []
}
```

For single-scenario runs, top-level `state`, `result`, and `output` are
populated. For multi-scenario runs, per-scenario details are always available in
`scenarios`. When a named request declares `OUTPUT` contracts, `result` contains
only those paths.

Host APIs use request names:

```python
rules.run_json({"order": order, "inventory": inventory}, request="fulfill order")
rules.run_trusted_json(state, request="fulfill order")
```

Trusted execution skips only named-request input and output boundary contract
validation. Behavior contracts, runtime type checks, request/scenario
assertions, and ordinary runtime errors still apply.

## Inspection And Host Type Generation

`gwt inspect --json` exposes named requests under `requests`. Each request
reports its input bindings, output bindings, and counts for local setup,
`WHEN` calls, and postconditions. It does not expose inferred entry candidates.

`gwt types file.gwt --language typescript` emits TypeScript declarations from
records, one-of records, and named requests. `--language python` emits Python
`TypedDict` helpers and a program-specific client wrapper from the same checked
contracts. Named requests generate:

- one input interface per request, such as `FulfillOrderRequest`
- one output interface per request, such as `FulfillOrderOutput`
- `GwtRequestName`
- `GwtRequests`
- `GwtOutputs`
- `GwtRequest`
- `GwtOutput`

Generated TypeScript maps `integer` and `number` to `number`, and maps
`decimal` to `string` at the JSON boundary.
Generated Python maps `integer` to `int`, `number` to `int | float`, and
`decimal` to `str` at the JSON boundary.

Generated host types are integration helpers only. The `.gwt` source remains
the normative behavior and contract artifact.

## Removed v0.1 Boundary Forms

These forms are not part of the v0.2 public interface:

- top-level `REQUEST path is Type`
- top-level `OUTPUT path is Type`
- `EXPORT name as behavior call`
- CLI `--entry`
- API `entry=...`
- inferred entry candidates
- generated `GwtEntry`

Use a named `REQUEST <natural phrase>` block and invoke it with `--request` or
`request=...`.
