# GWT Language Specification v0.1

Status: implemented.

GWT v0.1 is an executable behavior language built from `GIVEN`, `WHEN`, and
`THEN` forms. The full EBNF is maintained in [../grammar.md](../grammar.md);
this document fixes the behavior and tooling contracts for the v0.1 surface.

## Source Files

- Source files are UTF-8 text.
- `#` starts a comment. Comments run to the end of the line.
- Blank lines and comments do not affect execution.
- Indentation is significant and uses two spaces per level.
- Top-level forms start at column 1.
- A formatted file ends with one trailing newline.

`gwt format` is the canonical formatter for v0.1. It validates the file with
the parser, normalizes whitespace and table columns, and validates the formatted
result before writing. Formatting is syntax-oriented, so request files may
reference records supplied by a separate rules file.

## Program Shape

A file may contain these top-level forms:

- optional `PROGRAM` metadata
- zero or more `USE` imports
- zero or more `RECORD` contracts, including one-of records
- zero or more `REQUEST` / `OUTPUT` program contracts
- zero or more block-form `WHEN` behavior definitions
- optional `BACKGROUND`
- zero or more explicit `SCENARIO` blocks
- or one implicit `Main` scenario when no explicit scenario exists

Imports contribute record and behavior definitions. Imported scenarios do not run.
`BACKGROUND` must appear before explicit scenarios. `EXAMPLES` attaches to the
current scenario.

## Execution Model

Each scenario runs independently with fresh state:

1. Register behavior definitions.
2. Run `BACKGROUND` and scenario `GIVEN` setup.
3. Validate `REQUEST` contracts.
4. Run `BACKGROUND` and scenario `WHEN` steps.
5. Validate `OUTPUT` contracts after `WHEN` execution.
6. Evaluate `BACKGROUND` and scenario `THEN` assertions.

When a scenario contains an `EXAMPLES` table, each row creates one scenario run.

## Types

Supported type syntax:

- `number`
- `text`
- `boolean`
- `list`
- `any`
- a declared record name, including a one-of record name
- `list<TypeName>`, where `TypeName` is a primitive type or declared record name
- literal unions such as `"new" | "approved" | "denied"`

GWT v0.1 has no source-level `null` literal and no nullable type modifier.
JSON input may contain null values at raw boundaries, but null only satisfies an
`any` contract. It does not satisfy primitive, record, typed-list, one-of, or
literal-union contracts.

Records define state shape only. They do not define methods. `DTO` is accepted
as a legacy alias for `RECORD`; `gwt format` emits the canonical `RECORD`
spelling.

Within a `RECORD`, field paths must not overlap. A field may be either a typed
leaf or a parent for nested fields, not both:

```gwt
RECORD Account
  owner: text
    name: text # invalid: owner.name overlaps owner
```

One-of records model values that have one active kind:

```gwt
RECORD Statement is one of
  let_number:
    name: text
    value: number
  print_text:
    text: text
```

At runtime a one-of value is a record with an automatic `kind` field plus only
the fields for that kind, such as `{ "kind": "let_number", "name": "x",
"value": 2 }`. Validation rejects missing fields, unknown kinds, and fields
that do not belong to the active kind. In GWT setup, `kind` is added
automatically. In JSON input, include the same `kind` field shown in the stored
record shape.

## Behavior Signatures

Block-form `WHEN` defines behavior. Single-line `WHEN` executes behavior or a
built-in statement.

Preferred v0.1 signatures mark parameters explicitly:

```gwt
WHEN deposit <amount> into <account>
  GIVEN amount is number
  add amount to account.balance
```

Unmarked signature words are literals. For compatibility, signatures with no
explicit `<name>` parameters still run using the older implicit rule:
non-connector words after the behavior name are parameters, while connector
words such as `from`, `into`, `to`, `with`, `by`, `for`, `using`, and `as` are
literals. `gwt check` emits a warning for these implicit parameters; new
programs should use explicit `<name>` parameters.

Behavior contracts appear before executable statements:

```gwt
WHEN cart total for <cart>
  GIVEN cart is Cart
  THEN returns number
  RETURN cart.total
```

Behavior names cannot be built-ins or behavior-body keywords: `set`, `add`,
`subtract`, `append`, `count`, `sum`, `find`, `exists`, `print`, `LET`,
`REQUIRE`, `RETURN`, `PASS`, `IF`, `ELSE`, `FOR`, `FIND`, or `DEPENDING`.

## Statements

Behavior bodies support:

- `LET name be expression`
- `REQUIRE condition`
- `IF condition` / `ELSE`
- `FOR name in expression`
- `FOR name in expression WHERE condition`
- `FIND name in expression WHERE condition` with a required `ELSE`
- `DEPENDING ON expression` with `WHEN the kind is name` branches
- `RETURN expression`
- `PASS`
- behavior calls
- built-ins

Built-ins:

```gwt
set path to expression
add expression to path
subtract expression from path
append expression to path
count expression into path
sum expression into path
sum name.field in expression into path
find name in expression where condition into path
find optional name in expression where condition into path
exists name in expression where condition into path
print expression
```

`append`, `count`, `sum`, `find`, and `exists` operate on lists. `sum` requires
numeric items. Projected `sum` binds the leading name in `name.field` for each
list item and sums the projected numeric field. `find` stores the first
matching item and fails if no item matches. `find optional` leaves the target
unchanged when no item matches. `exists` stores a boolean.

Uppercase `FIND` is a behavior block for step-like matched-record updates:

```gwt
FIND item in invoice.items WHERE item.sku == requested_sku
  reserve item into fulfillment
ELSE
  add 1 to fulfillment.unknown_sku_count
```

It evaluates the list expression, binds the first item whose `WHERE` condition
is true as a local name for the first body, and executes the required `ELSE`
body when no item matches. If the matched item is a record from a list, dot-path
mutations through the local name update that record in place.

`PASS` is a no-op statement for behavior branches where success is meaningful
but no state change is needed.

`DEPENDING ON` branches by the active kind of a one-of record:

```gwt
DEPENDING ON statement
  WHEN the kind is let_number
    add statement.value to result.total
  WHEN the kind is print_text
    append statement.text to result.output
  ELSE
    append "unknown_statement" to result.errors
```

`ELSE` is required unless all known kinds are covered. Inside
`DEPENDING ON statement`, `WHEN the kind is let_number` means
`statement.kind` is `let_number`; GWT can check the fields that belong to that
kind.

## Tables

`GIVEN path are` creates a list of records from a pipe table. `GIVEN path are
RecordName` additionally validates every row against the record.

```gwt
GIVEN order.items are OrderItem
  | sku      | quantity |
  | "widget" | 1        |
```

`EXAMPLES` uses the same pipe table layout and substitutes `<name>` placeholders
inside scenario steps.

One-of record lists are built one value at a time because each kind can have
different fields:

```gwt
GIVEN program.statements is []

GIVEN program.statements contains a Statement of kind let_number
  name: "x"
  value: 2
```

The setup step appends the value to the list.

## API Payloads

Run payloads use a stable envelope:

```json
{
  "ok": true,
  "file": "rules.gwt",
  "request_file": "request.gwt",
  "scenario_count": 1,
  "scenarios": [],
  "state": {},
  "result": {},
  "output": []
}
```

For single-scenario runs, top-level `state`, `result`, and `output` are
populated. For multi-scenario runs, per-scenario details are always available in
`scenarios`. When `OUTPUT` contracts exist, `result` contains only declared
output paths; `state` keeps the full final runtime state.

Host adapters may run a program from JSON state plus an explicit entry behavior.
JSON state is loaded after `BACKGROUND` `GIVEN` setup and before `REQUEST`
validation. The entry behavior runs after `REQUEST` validation and before
`OUTPUT` validation. JSON-mode runs use the same payload envelope as `.gwt`
request-file runs. JSON null values should be normalized behind `any` request
boundaries before they are written into typed domain state.

Within `REQUEST` or within `OUTPUT`, contract paths must not overlap. Declare
either the whole record path or explicit leaf paths, not both:

```gwt
REQUEST cart is Cart
AND cart.total is number # invalid: cart.total overlaps cart
```

Request and output contracts are separate directions, so a `REQUEST` path may
overlap an `OUTPUT` path.

## Host Type Generation

`gwt types file.gwt --language typescript` emits TypeScript declarations from
the parsed and checked GWT contracts. `RECORD` declarations become interfaces,
one-of records become discriminated unions, `REQUEST` declarations become
`GwtRequest`, `OUTPUT` declarations become `GwtOutput`, and callable behavior
entries inferred from `REQUEST` paths become `GwtEntry`.
Generated TypeScript uses nested object shape for dotted contract paths. Raw
CLI JSON input may still provide state through dotted path keys, such as
`"cart.total"`, or through nested objects that produce the same state.

Generated host types are integration helpers only. The `.gwt` source remains
the normative behavior and contract artifact.

## Formatter Rules

The v0.1 formatter:

- trims trailing whitespace
- removes leading and trailing blank lines
- collapses multiple blank lines to one
- normalizes spacing after language keywords
- normalizes spacing after built-in statement names
- normalizes record field spacing around `:`
- aligns contiguous pipe tables
- preserves full-line and inline comments according to parser comment rules
- writes one final newline

The formatter is intentionally conservative. It does not reorder declarations,
rewrite behavior names, or convert implicit parameters to explicit parameters.
