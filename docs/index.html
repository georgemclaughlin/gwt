Specs you can run

GWT

In GWT, the spec is the program. Define the input contract, run named behavior, and return typed results from the same executable file.

The same file can also carry GIVEN / WHEN / THEN scenarios for tests. Capture real runs and compare behavior changes without creating a second implementation of the rules.

{
  "account": {
    "balance": 100,
    "status": "open"
  },
  "amount": 30
}
RECORD Account
  balance: number
  status: "open" | "closed"
REQUEST withdraw from account
  GIVEN account is Account
  AND amount is number
  WHEN withdraw amount from account
  OUTPUT account is Account
WHEN withdraw <amount> from <account>
  GIVEN account is Account
  REQUIRE account.status is "open"
  AND account.balance is at least amount
  subtract amount from account.balance
{
  "ok": true,
  "result": {
    "account": {
      "balance": 70,
      "status": "open"
    }
  }
}

How it works

Write It. Run It. Check It.

A GWT file shows the setup, the behavior, the input and output, and the examples that prove it works.

Walk through the basics

State Is Visible

Records and tables show the data the behavior reads and writes.

Behavior Has Names

Reusable WHEN blocks read like real workflow steps.

JSON Has A Shape

REQUEST says what input is required. OUTPUT says what result is returned.

Failure Is Clear

Missing data and bad shapes fail loudly instead of turning into silent defaults.

Examples Prove It

Scenarios live in the same file, so examples can be read and run in CI.

Evidence Stays Reviewable

Captured Execution Cases preserve what ran; corpora name the cases that matter for repeatable old/new review.

Try it

Run It Locally

Validate The Module

Check syntax, contracts, formatting, and embedded scenarios before host code runs.

python -m gwtlang validate \
  examples/vendor_onboarding/rules.gwt \
  --import-root examples/vendor_onboarding \
  --no-absolute-imports

Call It Like An App

Send JSON state to a named request and receive the stable result envelope.

python -m gwtlang run \
  examples/vendor_onboarding/rules.gwt \
  --json-input examples/vendor_onboarding/request.json \
  --request "review vendor" \
  --json

Generate Host Types

Create TypeScript declarations or Python helpers from checked request and output contracts.

python -m gwtlang types \
  examples/vendor_onboarding/rules.gwt \
  --language typescript \
  --output vendor-onboarding.d.ts

Run A Typed Host

Use the generated Python client wrapper to call the same named request.

python examples/vendor_onboarding/host_app.py

Serve A Standard HTTP Boundary

Use OpenAPI and gwt serve as the primary cross-language integration path.

python -m gwtlang openapi \
  examples/deployable_api/rules.gwt \
  --output openapi.json

python -m gwtlang serve \
  examples/deployable_api/rules.gwt \
  --port 8080

Capture Review Evidence

Record a real request as an Execution Case, then render a replay-verified local dossier.

python -m gwtlang capture \
  examples/vendor_onboarding/rules.gwt \
  --json-input examples/vendor_onboarding/request.json \
  --request "review vendor" \
  --output vendor-review.execution-case.json

python -m gwtlang workbench \
  vendor-review.execution-case.json \
  --program examples/vendor_onboarding/rules.gwt \
  --output vendor-review.html

Boundaries

What GWT Is Not

GWT is not SQL, not OPA, and not a replacement for a general-purpose language. It is for workflows where the steps and checks should stay readable and runnable.
